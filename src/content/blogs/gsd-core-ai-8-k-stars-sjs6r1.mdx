## 一、开篇：AI 写代码越来越慢，最后还跑偏

用 Claude Code 或 Cursor 写过中型项目的开发者，大多经历过这样一个过程：项目刚启动时，AI 助手反应迅速、代码质量在线；可一旦上下文累积到几万 token，模型的输出开始变慢、开始「幻觉」、开始忘记你最初的架构意图。这是 AI 工程领域知名的 **context rot（上下文腐烂）** 问题——当上下文窗口被填满，模型质量会不可逆地滑落。

更棘手的是：大多数 AI 编程工作流缺乏结构化记忆，跨会话上下文全部丢失；同时也缺少一个「验收环节」来确保生成的代码真的能跑。结果就是，AI 一顿猛写，PR 提上去后 bug 一堆，开发者反过来还要替它擦屁股。

有没有一套系统能把这三个问题一次性解决？GitHub 上 8K+ Stars 的 **GSD Core** 正是为此而生。

## 二、项目简介：让 AI 编程从「能用」走向「可靠」

GSD Core 把自己定位为「轻量级的元提示（meta-prompting）、上下文工程（context engineering）与规范驱动开发框架」，核心使命写得很直白——**Git. Ship. Done.**

它的四大关键词：

- **上下文工程**：对抗 context rot，让模型长期保持高质量输出
- **规范驱动**：先讨论、再计划、再执行，流程纪律严明
- **多运行时兼容**：原生支持 Claude Code、Codex、Cursor、Copilot、Windsurf、Kimi CLI、Antigravity CLI、Kilo 等 10+ AI 编程工具
- **MIT 开源**：协议宽松，社区驱动

GSD Core 在 GitHub 已斩获 **8128 Stars**，最新版本 1.7.0，提供英、葡、中、日、韩五种语言文档，生态成熟度肉眼可见。

## 三、核心功能深度解析

### 1. 五阶段循环：把混乱的 AI 编程拆成可复用的工艺

GSD Core 把每一个里程碑拆成 5 个步骤依次执行：**Discuss → Plan → Execute → Verify → Ship**。先在 Discuss 阶段敲定实现决策；Plan 阶段做研究、分解任务并校验上下文是否仍然「新鲜」；Execute 阶段以并行波次运行计划，每个执行子智能体都从一块干净的 200K token 上下文起步；Verify 阶段实地走查产出代码，自动诊断并产出修复方案；最后 Ship 阶段创建 PR、归档 phase，再开启下一轮。

这套循环的最大价值，是把「AI 写代码」从一次性的灵光乍现变成了可持续的工程节奏。

### 2. 上下文工程：每个执行体都「重置记忆」

针对 context rot，GSD Core 采用了一个看似暴力却极有效的策略——**把所有重活放到 fresh-context subagent 里跑**。主会话只承担轻量调度，把研究与执行外包给全新上下文的子智能体。配合 `STATE.md`、`CONTEXT.md` 等结构化产物跨会话持久化，主会话始终保持「轻盈」，从而规避上下文污染。

### 3. 跨运行时适配：一次配置，处处可用

无论你团队用的是 Claude Code、OpenCode 还是 Cursor，GSD Core 都通过统一的安装器适配。命令行只需 `npx @opengsd/gsd-core@latest`，按提示选择运行时与安装范围（全局/项目）即可生效。官方文档明确警告：**不要直接拷贝 `agents/` 或 `commands/` 文件**，必须走安装器以保证跨运行时兼容性。

### 4. 双场景入口：从 0 到 1 与从 1 到 N 同样顺手

- `/gsd-new-project`：绿地项目启动器
- `/gsd-onboard`：存量代码库接入器

无论你是开新坑还是接手祖传代码，都能找到匹配的引导流程。

## 四、技术亮点与性能数据

GSD Core 的架构亮点集中在三件事：

- **200K token 全新上下文隔离**：每个 executor 子智能体在干净上下文中启动，从源头避免 context rot
- **结构化状态持久化**：`STATE.md` 与 `CONTEXT.md` 让跨会话记忆可追溯、可恢复
- **强验证闭环**：Verify 阶段会主动遍历已构建产物，发现问题即生成 fix plan

兼容性方面，GSD Core 同时支持 Claude Code、OpenCode、Antigravity CLI、Kimi CLI、Kilo、Codex、Copilot、Cursor、Windsurf 等主流 AI 编程工具，覆盖度在同类框架中处于第一梯队。CI 流水线通过 GitHub Actions 全量跑通，测试徽章常亮。

## 五、适用场景与人群

**适合谁**：

- 用 AI 助手开发中型及以上项目的个人开发者与小团队
- 在多个 AI 编程工具间切换、想要统一工作流的工程师
- 重视代码质量、需要明确「验收」环节的技术 Lead

**具体场景**：

1. **新项目冷启动**：用 `/gsd-new-project` 一次性跑通从规划到 PR 的完整流程
2. **存量代码治理**：用 `/gsd-onboard` 把祖传仓库接入 GSD Core，逐步重塑为规范驱动
3. **跨工具协作**：团队成员分别用 Claude Code 与 Cursor，但共享同一套 phase 节奏

**不适合谁**：单文件脚本级别的玩具项目，或完全不接受 AI 介入的传统开发者。

## 六、竞品对比

| 维度 | GSD Core | 普通 AI Coding 助手 | 其他 spec-driven 框架 |

GSD Core 在「上下文工程 + Verify 闭环 + 多运行时」三个维度形成明显组合优势，特别适合追求长期可靠性的工程团队。

## 七、如何快速上手

```bash
npx @opengsd/gsd-core@latest
```

按提示选择运行时（Claude Code / Cursor / Codex 等）与安装范围（全局或项目本地）。如果你的运行环境没有 Node.js，可参考官方文档 [Install on your runtime](https://opengsd.net)。

安装完成后：

- 新项目：`/gsd-new-project`
- 存量代码：`/gsd-onboard`

**进阶建议**：新手先跟 [Your first project](https://opengsd.net) 走一遍从安装到首个 PR 的完整流程；接手老仓库则看 [Onboarding an existing codebase](https://opengsd.net)。遇到问题查 [recover-and-troubleshoot](https://opengsd.net)。
